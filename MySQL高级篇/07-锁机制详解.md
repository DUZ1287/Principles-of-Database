# 锁机制详解

> **这是高级篇最核心模块之一！** 锁机制是并发控制的核心，也是面试最常考的部分。

## 一、这个知识点是什么

数据库锁是解决并发冲突的核心机制。当多个事务同时读写同一数据时，锁保证数据的一致性和隔离性。

## 二、为什么要学它

- 锁机制是理解 MySQL 并发能力的关键
- 死锁排查是 DBA 的日常
- 行锁、间隙锁、临键锁是面试高频考点

---

## 三、核心内容

### 3.1 锁概述（P173）

**并发问题与锁**：

| 并发场景 | 问题 | 解决方案 |
|---|---|---|
| 读-读 | 无冲突 | 不需要锁 |
| 读-写 | 脏读、不可重复读 | MVCC（非锁定读） |
| 写-写 | 丢失更新 | 排他锁（X 锁） |

**悲观锁 vs 乐观锁**：

| 对比 | 悲观锁 | 乐观锁 |
|---|---|---|
| 思想 | 假定冲突一定发生，先锁再说 | 假定冲突不一定发生，提交时检测 |
| 实现 | InnoDB 行锁（`SELECT ... FOR UPDATE`） | 应用层版本号/时间戳 |
| 适用场景 | 写多读多、冲突频繁 | 读多写少、冲突较少 |

### 3.2 S 锁与 X 锁（P174）

| 锁类型 | 英文 | 别称 | 特点 |
|---|---|---|---|
| **S 锁** | Shared Lock | 读锁/共享锁 | 多个事务可同时持有 |
| **X 锁** | Exclusive Lock | 写锁/排他锁 | 独占，其他事务不能加任何锁 |

```sql
-- 加 S 锁
SELECT * FROM employees WHERE id = 1 LOCK IN SHARE MODE;

-- 加 X 锁
SELECT * FROM employees WHERE id = 1 FOR UPDATE;
```

**兼容性矩阵**：

|  | 请求 S 锁 | 请求 X 锁 |
|---|---|---|
| 已有 S 锁 | ✅ 兼容 | ❌ 冲突 |
| 已有 X 锁 | ❌ 冲突 | ❌ 冲突 |

### 3.3 表级锁（P175~P176）

#### 表锁

```sql
LOCK TABLES employees READ;   -- 表级 S 锁（只读）
LOCK TABLES employees WRITE;  -- 表级 X 锁（独占）
UNLOCK TABLES;                -- 释放
```

#### 意向锁（Intention Lock）

InnoDB 自动加的表级锁，表示"事务打算对某些行加 S/X 锁"。

| 意向锁 | 含义 |
|---|---|
| **IS**（意向共享锁） | 准备在某些行加 S 锁 |
| **IX**（意向排他锁） | 准备在某些行加 X 锁 |

**作用**：快速判断表级锁冲突，避免逐行扫描。

**兼容矩阵**：

|  | IS | IX | S | X |
|---|---|---|---|---|
| **IS** | ✅ | ✅ | ✅ | ❌ |
| **IX** | ✅ | ✅ | ❌ | ❌ |
| **S** | ✅ | ❌ | ✅ | ❌ |
| **X** | ❌ | ❌ | ❌ | ❌ |

#### 自增锁（AUTO-INC Lock）

- 插入自增列时获取，保证自增值连续唯一
- 插入语句结束后立即释放（不是事务结束时）

#### 元数据锁（MDL）

- DDL 操作自动加 MDL 锁，保护表结构
- 读操作加 MDL_SHARED_READ，写操作加 MDL_EXCLUSIVE
- **小心**：大查询在跑时，DDL 会被 MDL 阻塞！

### 3.4 行级锁（P177~P178）

#### 记录锁（Record Lock）

- 锁定某一行索引记录
- `SELECT ... WHERE id = 1 FOR UPDATE` → 锁住 id=1

#### 间隙锁（Gap Lock）

- 锁定索引记录之间的"间隙"
- 防止其他事务在间隙中插入新记录
- **REPEATABLE READ 下防幻读的关键！**

```sql
-- 表中现有 ID：1, 3, 5, 7
SELECT * FROM employees WHERE id > 3 AND id < 7 FOR UPDATE;
-- 锁定区间：(3, 5) 和 (5, 7)
-- 其他事务无法在这两个区间插入新记录
```

#### 临键锁（Next-Key Lock）

**= 记录锁 + 间隙锁**，InnoDB 默认的行锁类型。

| 查询条件 | 锁住的范围 |
|---|---|
| `id = 5` | (上一索引, 5] |
| `id > 5 AND id < 10` | (5, 10) |
| `id <= 10` | (-∞, 10] |

#### 插入意向锁（Insert Intention Lock）

- 插入操作前获取，是 Gap 锁的变种
- 多个事务在同一间隙等待时，只要插入位置不同就能并发等待

### 3.5 乐观锁实现（P179）

```sql
-- 方式1：版本号字段
-- 读取时获取 version=1
SELECT name, salary, version FROM employees WHERE id = 1;

-- 更新时检查 version
UPDATE employees SET salary = 6000, version = version + 1
WHERE id = 1 AND version = 1;
-- 影响行数 = 0 → 乐观锁冲突，需要重试

-- 方式2：时间戳
UPDATE employees SET salary = 6000, update_time = NOW()
WHERE id = 1 AND update_time = '2024-01-01 10:00:00';
```

### 3.6 隐式锁与显式锁（P180）

| 类型 | 说明 | 示例 |
|---|---|---|
| **显式锁** | 手动加锁 | `SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE` |
| **隐式锁** | InnoDB 自动加锁 | UPDATE、DELETE 自动加 X 锁 |

### 3.7 全局锁与死锁（P181）

#### 全局锁

```sql
FLUSH TABLES WITH READ LOCK;  -- 全局读锁，常用于备份
UNLOCK TABLES;
```

> 生产环境用 `mysqldump --single-transaction`（基于 MVCC 一致性备份），不需要全局锁。

#### 死锁（Deadlock）

两个事务互相等待对方持有的锁，形成死循环。

```sql
-- 死锁示例
-- 事务A：锁 id=1，等 id=2
-- 事务B：锁 id=2，等 id=1 → 死锁！
```

**死锁处理**：

| 机制 | 说明 |
|---|---|
| **死锁检测** | InnoDB 用"等待图"算法检测 |
| **等待超时** | `innodb_lock_wait_timeout`（默认 50 秒） |
| **自动回滚** | 回滚 undo log 较少的事务（代价小） |

**避免死锁**：
- 按固定顺序访问表和行
- 事务尽量短
- 一次性锁定所有需要的资源

```sql
-- 查看死锁日志
SHOW ENGINE INNODB STATUS;
```

## 四、容易出错的地方

1. **间隙锁只在 REPEATABLE READ 及以上级别存在**
2. **行锁是加在索引上的**：没有索引时，行锁退化为表锁
3. **FOR UPDATE 和 LOCK IN SHARE MODE 是当前读**：读的是最新数据
4. **死锁不是错误**：InnoDB 会自动处理，但要避免频繁死锁
5. **MDL 锁容易被忽略**：大查询期间做 DDL 会被阻塞

## 七、总结

- S 锁（读锁）共享，X 锁（写锁）独占
- 行锁：记录锁 + 间隙锁 = 临键锁
- 意向锁是表锁和行锁之间的桥梁
- 行锁加在索引上，没有索引退化为表锁
- 死锁靠等待图检测 + 自动回滚解决

### 和哪些知识点有关

- **事务隔离级别** → 锁是实现隔离性的手段
- **MVCC** → MVCC 减少锁需求，提高并发
- **索引** → 行锁加在索引上
- **EXPLAIN** → 查看 SQL 是否加锁

### 初学者容易误解什么

1. 以为"行锁就是锁行"——实际是锁索引记录
2. 以为 FOR UPDATE 是"查询"——实际是当前读+加 X 锁
3. 以为间隙锁到处都有——只有 REPEATABLE READ 及以上才有

### 实际项目中可能怎么用

- 高并发扣库存用 `SELECT ... FOR UPDATE` 加悲观锁
- 秒杀场景用乐观锁（版本号）减少锁等待
- 定期检查 `SHOW ENGINE INNODB STATUS` 排查死锁
