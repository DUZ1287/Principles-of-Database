# 索引深入原理与B+树

> **这是高级篇最核心、最硬核的模块！** 索引是 MySQL 性能优化的基石，深入理解 B+ 树才能真正掌握 SQL 优化。

## 一、这个知识点是什么

索引是帮助 MySQL 高效获取数据的**排好序的数据结构**。本模块从"为什么需要索引"出发，逐步推导出 B+ 树的设计原理，并深入 InnoDB 的数据存储结构。

## 二、为什么要学它

- 索引是**面试频率最高**的 MySQL 知识点（没有之一）
- 不理解 B+ 树就无法理解索引优化
- 聚簇索引、二级索引、回表、覆盖索引是面试必考

## 三、核心内容

### 3.1 索引的优缺点（P115）

**优点**：
- 大幅提升检索速度（100 万数据：全表扫描百万次 IO → B+ 树 3~4 次 IO）
- 加速排序和分组（ORDER BY / GROUP BY）
- 加速多表 JOIN

**缺点**：
- 占用磁盘空间（索引文件可能比数据还大）
- 降低写入速度（INSERT/UPDATE/DELETE 要同时维护索引）

### 3.2 索引数据结构演进（P116~P117）

| 方法 | 数据结构 | 查询复杂度 | 问题 |
|---|---|---|---|
| 线性查找 | 数组/链表 | O(n) | 百万数据百万次比较 |
| 二分查找 | 有序数组 | O(log₂n) | 插入删除要移动大量数据 |
| 二叉树/BST | 二叉树 | O(log₂n) | 极端情况退化成链表 |
| AVL 树 | 平衡二叉树 | O(log n) | 每节点只两个分支，树太高 |
| B 树 | 多叉平衡树 | O(log_m n) | 非叶子节点也存数据，浪费空间 |
| **B+ 树** | 优化 B 树 | O(log_m n) | **只有叶子节点存数据，最矮胖** |

### 3.3 B+ 核心优势（P120）

**B+ 树 vs 其他数据结构**：

| 数据结构 | 查询复杂度 | 范围查询 | 排序 | 适用引擎 |
|---|---|---|---|---|
| **B+ 树** | O(log_m n) | 支持（叶子链表） | 支持 | InnoDB / MyISAM |
| **Hash** | O(1) 平均 | 不支持 | 不支持 | MEMORY |
| **AVL** | O(log n) | 支持 | 支持 | 内存数据库 |
| **红黑树** | O(log n) | 支持 | 支持 | Java HashMap |

**B+ 树为什么适合 MySQL？三个核心优势**：

1. **更矮胖，IO 更少**：每个节点可存 1170 个键（16KB 页），100 万数据只需 3 层（3 次 IO）
2. **叶子节点链表，范围查询快**：所有数据在叶子形成有序链表
3. **非叶子节点只存索引**：一次 IO 能读入更多索引项

**Hash 索引的适用场景**：

| 场景 | Hash | B+ 树 |
|---|---|---|
| 等值查询（=） | 极快 O(1) | O(log n) |
| 范围查询（> < BETWEEN） | 无法使用 | 支持 |
| 模糊查询（LIKE） | 无法使用 | 支持 |
| 排序（ORDER BY） | 无法使用 | 支持 |

### 3.4 聚簇索引与二级索引（P118~P119）

#### 聚簇索引（Clustered Index）

- 即主键索引
- 叶子节点**存储完整的行数据**（数据即索引，索引即数据）
- 每张 InnoDB 表**只能有一个**聚簇索引

#### 二级索引（Secondary Index）

- 非主键列上的索引
- 叶子节点**存储主键值**（不是完整数据）
- 查询时需要**回表**：先在二级索引找主键，再去聚簇索引找完整数据

**回表流程**：

```
SELECT * FROM employees WHERE name = '张三';
  ↓
1. 二级索引(name) 找到 '张三' → 主键 ID=100
  ↓
2. 拿着 ID=100 去聚簇索引找完整行 → 回表
  ↓
3. 返回完整数据
```

**对比表**：

| 对比 | 聚簇索引 | 二级索引 |
|---|---|---|
| 叶子节点存什么 | 完整行数据 | 主键值 |
| 数量限制 | 每表只能 1 个 | 可有多个 |
| 查询效率 | 等值查询快 | 等值查询需回表 |

#### InnoDB vs MyISAM 索引结构

```
InnoDB:
  聚簇索引叶子 → [索引键 + 完整行数据]
  二级索引叶子 → [索引列 + 主键值] → 需要回表

MyISAM:
  所有索引叶子 → [索引键 + 行指针] → 指向数据文件
  索引文件和数据文件分离
```

### 3.5 联合索引与最左前缀原则（P118）

```sql
CREATE INDEX idx_dept_salary ON employees(dept_id, salary);
```

**最左前缀原则**：联合索引像按"拼音+声调+部首"排序，必须从最左列开始匹配。

```
索引: (dept_id, salary, hire_date)

✅ 能命中：
  WHERE dept_id = 10
  WHERE dept_id = 10 AND salary > 5000
  WHERE dept_id = 10 AND salary > 5000 AND hire_date > '2020-01-01'

❌ 不能命中：
  WHERE salary > 5000          -- 跳过了最左的 dept_id
  WHERE hire_date > '2020-01-01' -- 跳过了 dept_id
```

### 3.6 InnoDB 数据存储结构（P121~P127）

#### 存储层次（从大到小）

```
表空间（Tablespace）
├── 段（Segment）     → 数据段、索引段、回滚段
├── 区（Extent）      → 64 个连续页 = 1MB
├── 页（Page）        → 16KB（最小 IO 单位）
└── 行（Row）         → 数据行
```

#### 页的内部结构（P122~P124）

| 组成部分 | 大小 | 作用 |
|---|---|---|
| **File Header** | 38 字节 | 页号、上下页指针、校验和 |
| **Page Header** | 56 字节 | 槽数、记录数 |
| **Infimum + Supremum** | 26 字节 | 虚拟记录，界定边界 |
| **User Records** | 用户数据 | 实际行数据 |
| **Free Space** | 动态 | 空闲空间 |
| **Page Directory** | 动态 | 槽数组，加速页内二分查找 |
| **File Trailer** | 8 字节 | 校验和，检测页完整性 |

#### InnoDB 隐藏列（P123）

每行自动添加 3 个隐藏列：

| 隐藏列 | 大小 | 作用 |
|---|---|---|
| **DB_ROW_ID** | 6 字节 | 行 ID（没有主键时用） |
| **DB_TRX_ID** | 6 字节 | 事务 ID（MVCC 核心） |
| **DB_ROLL_PTR** | 7 字节 | 回滚指针（指向 Undo Log） |

> 这 3 个隐藏列共 19 字节，是 MVCC 实现的基础。

#### 行格式（P125~P126）

| 行格式 | 特点 | 使用场景 |
|---|---|---|
| **Compact** | 默认格式，节省空间 | 通用场景 |
| **Dynamic** | MySQL 5.7+ 默认 | 行溢出时只存指针 |
| **Compressed** | 压缩存储 | 存储空间紧张 |
| **Redundant** | 旧格式 | 遗留系统 |

**Compact 格式结构**：

```
变长字段长度列表 → NULL 标志位 → 记录头信息 → 列数据
```

#### 表空间类型（P127）

| 表空间 | 说明 |
|---|---|
| **系统表空间** | 默认，存储所有表和索引（ibdata1） |
| **独立表空间** | 每表一个 `.ibd` 文件（推荐） |
| **临时表空间** | 临时表和排序 |
| **Undo 表空间** | Undo Log 存储 |

## 四、容易出错的地方

1. **聚簇索引只能有一个**：不是主键就是第一个唯一索引，再不就是隐藏的 ROW_ID
2. **回表开销**：`SELECT *` 容易导致回表，尽量用覆盖索引
3. **最左前缀原则**：联合索引 (a,b,c)，查询 b=1 不走索引
4. **B+ 树层数**：千万级数据通常只需 3~4 层
5. **页大小**：InnoDB 默认 16KB，这是 IO 的最小单位

## 七、总结

- B+ 树是最适合磁盘存储的索引结构（矮胖、叶子链表、IO 友好）
- 聚簇索引存完整数据，二级索引存主键值（需要回表）
- 联合索引遵循最左前缀原则
- InnoDB 数据存储：表空间→区→页→行

## AI辅助思考

### 这个知识点真正重要的地方

**B+ 树是整个 MySQL 性能体系的基石。** 不理解 B+ 树，就无法理解索引优化、EXPLAIN 分析、索引失效等后续所有内容。面试中 "为什么用 B+ 树" 几乎是必问题。

### 和哪些知识点有关

- **前置知识**：二叉树、平衡二叉树、B 树的基本概念
- **后续知识**：索引创建与优化、EXPLAIN 分析、索引失效、覆盖索引、索引下推
- **底层基础**：页结构、行格式 → 理解数据在磁盘上怎么存的

### 初学者容易误解什么

1. 以为"索引越多越好"——索引占用空间，且降低写入性能
2. 以为"Hash 索引比 B+ 树快"——Hash 只能做等值查询，范围查询不行
3. 以为"聚簇索引就是主键索引"——如果没有主键，InnoDB 会选唯一索引或隐藏 ROW_ID
4. 忽略"回表"的开销——`SELECT *` 在有二级索引时可能导致大量回表

### 实际项目中可能怎么用

- 设计表时优先考虑主键（自增整型最佳）
- 高频查询字段建立联合索引，利用覆盖索引避免回表
- 理解页结构有助于理解为什么"顺序插入"比"随机插入"快
