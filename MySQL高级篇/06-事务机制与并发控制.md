# 事务机制与并发控制

## 一、这个知识点是什么

事务是数据库保证数据一致性的核心机制。本模块涵盖：
1. **事务基础**——ACID 特性、显式/隐式事务
2. **并发控制**——脏读、不可重复读、幻读、四种隔离级别
3. **事务日志**——Redo Log（持久性）和 Undo Log（原子性）

## 二、为什么要学它

- ACID 是**面试必考题**，几乎是 MySQL 面试的第一道题
- 隔离级别和并发问题是理解 MVCC 和锁机制的前提
- Redo/Undo 日志是 InnoDB 实现事务的核心

## 三、核心内容

### 3.1 ACID 四大特性（P161）

| 特性 | 英文 | 含义 | 实现机制 |
|---|---|---|---|
| **A 原子性** | Atomicity | 全部成功或全部失败 | Undo Log |
| **C 一致性** | Consistency | 事务前后状态一致 | 应用层 + InnoDB |
| **I 隔离性** | Isolation | 并发事务互不干扰 | 锁 + MVCC |
| **D 持久性** | Durability | 提交后数据永久保存 | Redo Log |

**形象举例**：ATM 转账——
- 原子性：扣款和加款要么都成功，要么都不发生
- 一致性：转账前后总金额不变
- 隔离性：多人同时转账不会互相影响
- 持久性：转账成功后断电也不会丢

**事务状态**：

```
活动（Active）→ 部分提交 → 已提交（Committed）
    ↓
  失败（Failed）→ 中止（Aborted）→ 回滚
```

### 3.2 显式事务与隐式事务（P162）

| 类型 | 说明 | 示例 |
|---|---|---|
| **隐式事务** | 单条 SQL 自动提交 | `autocommit=1`（默认） |
| **显式事务** | 手动控制事务边界 | `START TRANSACTION ... COMMIT/ROLLBACK` |

```sql
-- 显式事务
START TRANSACTION;
UPDATE accounts SET balance = balance - 1000 WHERE user_id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE user_id = 2;
COMMIT;  -- 或 ROLLBACK

-- 保存点
SAVEPOINT sp1;
-- ... 操作 ...
ROLLBACK TO sp1;  -- 回滚到保存点
```

**事务设计原则**：
- 事务尽量短，减少锁持有时间
- 事务中避免用户交互
- 事务中避免大批量操作

### 3.3 并发事务三大问题（P164）

| 问题 | 现象 | 严重程度 |
|---|---|---|
| **脏读（Dirty Read）** | 读到其他事务**未提交**的数据 | 严重 |
| **不可重复读** | 同一事务两次读，数据**值**变了（其他事务已提交修改） | 中等 |
| **幻读（Phantom Read）** | 同一事务两次读，数据**行数**变了（其他事务已提交插入/删除） | 中等 |

**三者对比**：

| 问题 | 焦点 | 原因 |
|---|---|---|
| 脏读 | 未提交数据 | 读了别人没 COMMIT 的数据 |
| 不可重复读 | 已提交数据的**值**变了 | 读了别人 COMMIT 后修改的值 |
| 幻读 | 已提交数据的**行数**变了 | 读了别人 COMMIT 后新增/删除的行 |

### 3.4 四种隔离级别（P164~P165）

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---|---|---|---|---|
| **READ UNCOMMITTED** | 可能 | 可能 | 可能 | 最快 |
| **READ COMMITTED** | 不可能 | 可能 | 可能 | 较快 |
| **REPEATABLE READ**（MySQL 默认） | 不可能 | 不可能 | 可能* | **默认** |
| **SERIALIZABLE** | 不可能 | 不不可能 | 不可能 | 最慢 |

> *MySQL 的 REPEATABLE READ 通过 MVCC + 间隙锁在很大程度上解决了幻读。

```sql
-- 查看隔离级别
SELECT @@transaction_isolation;  -- MySQL 8.0

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

**各隔离级别实现机制**：

| 隔离级别 | 实现方式 |
|---|---|
| READ UNCOMMITTED | 不加锁，直接读最新数据 |
| READ COMMITTED | 每次 SELECT 生成新 ReadView |
| REPEATABLE READ | 事务开始时生成 ReadView，整个事务复用 |
| SERIALIZABLE | 所有读操作加锁，强制串行 |

### 3.5 Redo Log（P169~P171）

#### 为什么需要 Redo Log

- 数据写入磁盘是**随机 IO**（慢）
- Redo Log 是**顺序 IO**（快）
- **WAL 原则**（Write-Ahead Logging）：先写日志，再写磁盘

```
事务修改数据 → 写入 Buffer Pool（内存）
    ↓
事务提交 → Redo Log 刷盘（顺序 IO，快）
    ↓
后台线程 → 脏页刷到数据文件（随机 IO，慢）
```

#### Redo Log 刷盘策略

| innodb_flush_log_at_trx_commit | 策略 | 安全性 | 性能 |
|---|---|---|---|
| **0** | 每秒刷盘 | 最差（丢 1 秒数据） | 最快 |
| **1**（默认） | 每次 COMMIT 都刷盘 | **最安全** | 较慢 |
| **2** | COMMIT 写 OS 缓存，每秒刷盘 | 中等 | 较快 |

> 生产环境建议设为 **1**（双 1 配置：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`）

### 3.6 Undo Log（P172）

**两大作用**：

| 作用 | 说明 |
|---|---|
| **事务回滚** | ROLLBACK 时恢复数据到修改前 |
| **MVCC** | 提供历史版本数据，实现快照读 |

**Undo Log 内容**：
- INSERT → 记录主键，回滚时 DELETE
- DELETE → 记录完整行，回滚时 INSERT
- UPDATE → 记录旧值，回滚时恢复

### Redo Log vs Undo Log 对比

| 对比维度 | Redo Log | Undo Log |
|---|---|---|
| 作用 | 恢复已提交事务 | 回滚未提交事务 |
| 内容 | 修改后的数据 | 修改前的数据 |
| 存储位置 | ib_logfile0/1 | Undo 表空间 |
| 逻辑 | 物理日志 | 逻辑日志 |
| 对应 ACID | 持久性（D） | 原子性（A） |

## 四、容易出错的地方

1. **脏读 vs 不可重复读**：脏读读的是未提交数据，不可重复读读的是已提交数据
2. **MySQL 默认隔离级别**：是 REPEATABLE READ，不是 READ COMMITTED
3. **Redo Log 刷盘策略**：生产环境必须设为 1
4. **Undo Log 不是立即删除**：事务提交后可能还需要保留（MVCC 用）
5. **WAL 原则**：先写日志再写磁盘，不是直接写磁盘

## 七、总结

- ACID：原子性靠 Undo Log，持久性靠 Redo Log，隔离性靠锁+MVCC
- MySQL 默认 REPEATABLE READ
- Redo Log 实现崩溃恢复（WAL 原则）
- Undo Log 实现事务回滚和 MVCC

## AI辅助思考

### 这个知识点真正重要的地方

事务是 MySQL 面试的**必考板块**，ACID 四特性 + 隔离级别 + Redo/Undo Log 是三位一体的知识体系。面试官经常从"ACID 是什么"开始，逐步深入到"怎么实现的"。

### 和哪些知识点有关

- **MVCC** → 基于 Undo Log 版本链，是隔离性的实现方式之一
- **锁机制** → 锁是隔离性的另一种实现方式
- **两阶段提交** → Redo Log + binlog 的协调
- **崩溃恢复** → 依赖 Redo Log

### 初学者容易误解什么

1. 以为一致性（C）是数据库自己保证的——其实需要应用层配合
2. 以为隔离级别越高越好——SERIALIZABLE 性能极差，几乎不用
3. 以为 Redo Log 和 binlog 是一回事——它们是不同的日志系统

### 实际项目中可能怎么用

- 转账、下单等操作用显式事务保证一致性
- 根据业务需求选择合适的隔离级别
- 理解 Redo Log 配置对数据安全的影响
