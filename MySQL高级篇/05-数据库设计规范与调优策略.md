# 数据库设计规范与调优策略

## 一、这个知识点是什么

本模块涵盖两个主题：
1. **数据库设计规范**——主键设计、范式理论、ER 建模、SQL 编写规范
2. **数据库调优策略**——分层优化思路、大表优化、参数调优

## 二、为什么要学它

- 项目开发中表设计是第一步，设计不好后续优化很痛苦
- 范式与反范式的权衡是实际项目中的常见决策
- 调优策略是 DBA 和后端工程师的必备技能

## 三、核心内容

### 3.1 主键设计（P150）

| 主键类型 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **自增主键** | 插入快、空间小、有序 | 不够分散、无法跨表 | **MySQL 默认首选** |
| **UUID** | 全球唯一 | 插入慢（随机 IO）、字符串大 | 分布式系统 |
| **雪花算法** | 有序+全局唯一 | 需要引入组件 | 分布式 ID |
| **业务主键** | 天然唯一 | 变更困难 | 特殊业务 |

> 自增主键像按顺序排队，B+ 树叶子自然有序，插入快。UUID 像随机插队，每次插入可能导致节点分裂。

### 3.2 范式理论（P151~P155）

#### 三大范式

| 范式 | 要求 | 示例 |
|---|---|---|
| **1NF** | 列不可再分 | "电话"列不能同时存"固话+手机" |
| **2NF** | 非主键列完全依赖主键 | 订单明细表中"产品名"只依赖"产品号"，不依赖"订单号"→ 拆表 |
| **3NF** | 非主键列之间无传递依赖 | 学生表中"班级名"依赖"班级号"，不直接依赖"学号"→ 拆表 |

**2NF 示例**：

```
❌ 违反：订单明细(订单号, 产品号, 产品名称, 产品价格)
  → 产品名称只依赖产品号

✅ 修正：订单明细(订单号, 产品号, 数量) + 产品(产品号, 名称, 价格)
```

**3NF 示例**：

```
❌ 违反：学生(学号, 姓名, 班级号, 班级名称)
  → 班级名称传递依赖学号

✅ 修正：学生(学号, 姓名, 班级号) + 班级(班级号, 班级名称)
```

#### 更高范式

| 范式 | 说明 | 实用频率 |
|---|---|---|
| **BCNF** | 任何决定因素都含候选键 | 偶尔用 |
| **4NF** | 消除多值依赖 | 极少用 |
| **5NF** | 消除连接依赖 | 几乎不用 |

> 实际工作中 **3NF 足够**，过度追求高级范式反而增加复杂度。

### 3.3 反范式化（P153）

为了性能，有意违反范式，增加冗余数据。

| 场景 | 做法 | 原因 |
|---|---|---|
| 电商订单查询 | 订单表冗余"用户名"、"商品名" | 避免每次 JOIN |
| 论坛帖子 | 帖子表冗余"回复数"、"最后回复时间" | 避免 count(*) |
| 数据分析 | 统计表冗余汇总数据 | 实时聚合太慢 |

**范式 vs 反范式**：

| 对比 | 范式化 | 反范式化 |
|---|---|---|
| 数据冗余 | 无 | 有 |
| 更新难度 | 改一处 | 需改多处 |
| 查询性能 | 可能多表 JOIN | 少 JOIN 或单表 |
| 存储空间 | 省空间 | 占空间 |

### 3.4 ER 建模（P156）

| ER 关系 | 转换方式 |
|---|---|
| 一对一 | 外键放任意一方 |
| 一对多 | 外键放"多"的一方 |
| 多对多 | **中间表**，两个外键组成主键 |

### 3.5 数据库设计原则（P157）

| 原则 | 说明 |
|---|---|
| **适度冗余** | 查询多的字段适当冗余，减少 JOIN |
| **冷热分离** | 热数据和冷数据分开存储 |
| **大字段分离** | TEXT/BLOB 等大字段单独成表 |
| **避免过度范式** | 3NF 足够 |
| **预留扩展字段** | 预留 1~2 个扩展字段应对需求变更 |

**SQL 编写规范**：

| 规范 | 说明 |
|---|---|
| 关键字大写 | `SELECT`、`WHERE` |
| 表名/列名小写+下划线 | `employee_info` |
| 避免 `SELECT *` | 只查需要的列 |
| WHERE 条件索引列在前 | 提高过滤效率 |
| 避免 WHERE 中使用函数 | 会导致索引失效 |
| 批量操作用 LIMIT 分批 | 避免大事务 |
| JOIN 时小表驱动大表 | 减少扫描量 |

### 3.6 数据库调优策略（P159~P160）

#### 调优四层次（自顶向下）

```
第1层：SQL 查询优化（改 SQL、加索引）        ← 投入最小，收益最大
  ↓
第2层：数据库结构优化（分库分表、字段类型）   ← 收益大，改动大
  ↓
第3层：MySQL 配置优化（Buffer Pool、线程池）  ← 需深入理解
  ↓
第4层：硬件/OS 升级（SSD、内存、CPU）        ← 成本最高
```

#### 硬件优化

| 硬件 | 优化方向 |
|---|---|
| **磁盘（最关键）** | SSD，随机读写提升 100 倍 |
| **内存** | 扩大 Buffer Pool |
| **CPU** | 多核，支持更多并发 |
| **网络** | 万兆网卡 |

#### 关键参数调优

```sql
-- Buffer Pool 大小（通常物理内存的 50%~75%）
innodb_buffer_pool_size = 4G

-- Redo 日志大小
innodb_log_file_size = 512M

-- 最大连接数
max_connections = 500

-- 临时表大小
tmp_table_size = 64M
```

#### 大表优化策略

| 策略 | 说明 | 适用场景 |
|---|---|---|
| **垂直拆分** | 宽表拆窄表 | 冷热字段分离 |
| **水平拆分** | 大表拆小表 | 单表超千万行 |
| **分区表** | 逻辑一表，物理多文件 | 按时间/范围查询 |
| **读写分离** | 主库写，从库读 | 读多写少 |
| **归档历史数据** | 旧数据移到归档表 | 日志、历史订单 |

**分区表示例**：

```sql
CREATE TABLE orders (
  id INT,
  order_date DATE,
  amount DECIMAL(10,2)
) PARTITION BY RANGE (YEAR(order_date)) (
  PARTITION p2023 VALUES LESS THAN (2024),
  PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p2025 VALUES LESS THAN MAXVALUE
);
```

## 四、容易出错的地方

1. **范式过度**：为了 3NF 拆太多表，JOIN 性能反而差
2. **反范式滥用**：到处冗余导致数据不一致
3. **调优顺序**：上来就升级硬件，应该先优化 SQL
4. **Buffer Pool 大小**：设太大导致操作系统 swap

## 七、总结

- 主键推荐自增整型，分布式场景用雪花算法
- 范式到 3NF 足够，必要时反范式化
- 调优优先级：SQL 优化 > 结构优化 > 参数优化 > 硬件升级
- 大表优化：垂直拆分、水平拆分、分区表、读写分离
